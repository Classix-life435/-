# 営業週次レポート（Slack・Gmail → Excel）

Slackとメールに流れている商談の断片を、**そのまま読める一枚の表**にする。
使う人は営業会議の直前にこれを開くので、大事なのは網羅性よりも
「どの案件が今どうなっていて、次に誰が何をするのか」が一目で分かること。

仕事は2本立てになっている。どちらか一方だけを頼まれることもある。

- **案件管理**（手順1〜7）… Slack中心。進行中の商談を案件表にする
- **リード管理**（手順8〜11）… Gmail中心。問い合わせを製品別に振り分け、返信下書きを作り、進捗を追う

## 出力するもの

1. **Excel**（`営業進捗_YYYYMMDD.xlsx`）— サマリ／案件一覧／リード一覧の3シート
2. **Gmailの下書き** — 要返信のリードへの返信案（**送信はしない**）
3. **Gmailラベル** — リードの進捗を `リード/…` ラベルで記録
4. **Slackサマリ投稿** — `#営業進捗管理` にテキストで要点を投稿
5. 生成したxlsxをユーザーに渡す（`SendUserFile` があればそれで、なければ保存先パスを伝える）

## 進め方

### 1. 集計期間を決める

既定は **直近1週間**：前週の金曜15:00（JST）〜 実行時点。
ユーザーが期間を指定したらそちらを優先する。

Slackの `oldest` / `latest` はUnix秒なので変換しておく：

```bash
python3 -c "
from datetime import datetime, timedelta, timezone
jst = timezone(timedelta(hours=9))
end = datetime.now(jst)
start = end - timedelta(days=7)
print('oldest', int(start.timestamp()))
print('latest', int(end.timestamp()))
print(start.strftime('%Y-%m-%d %H:%M'), '->', end.strftime('%Y-%m-%d %H:%M'))
"
```

### 2. 対象チャンネルを毎回探す

チャンネルは固定しない。営業の話は専用チャンネルだけでなく顧客名チャンネル
（`#株式会社◯◯`、`#◯◯市` など）でも進むので、取りこぼさないよう2方向から探す：

- `slack_search_public_and_private` で **メッセージ本文** を期間内検索する。
  **キーワードは1語ずつ、別々に検索する。** Slack検索はスペース区切りがANDなので、
  `商談 見積 提案 受注` のようにまとめて投げると全部を含むメッセージだけが対象になり、
  ほぼ確実に0件になる。実際にこの失敗をした。

  ```
  query="案件 after:2026-09-04"    sort="timestamp"
  query="見積 after:2026-09-04"    sort="timestamp"
  query="商談 after:2026-09-04"    sort="timestamp"
  ```

  回す語：`案件` `商談` `見積` `提案` `受注` `失注` `契約` `発注` `稟議` `デモ` `アポ` `訪問` `導入` `御中` `様`
  → ヒットしたメッセージが載っているチャンネルが、その週の実際の営業現場。
- `slack_search_channels`（`channel_types: public_channel,private_channel`）で
  `営業` `案件` `株式会社` などの**チャンネル名**も拾う。
  ただしチャンネル名検索は取りこぼしがある（`#営業案件` が `営業` で出てこないことがあった）ので、
  **メッセージ本文検索の方を主、チャンネル名検索を従として扱う。**

このワークスペース（ragnize）で実際に営業の話が進んでいたチャンネルの例：
`#営業案件` `#営業進捗管理` `#営業kpi` `#fde案件` `#nttプロジェクト` `#ロードカー営業`
`#契約書法務` `#qr-phone` `#ジャパックス` および顧客名チャンネル。
これは**当たりをつけるためのヒントであって固定リストではない**。毎回の検索結果を優先する。

両者のチャンネルIDを重複排除する。多すぎる場合は
「営業系チャンネル」＋「期間内に営業キーワードのヒットがあったチャンネル」を優先し、
**最大15チャンネル程度**に絞る。絞った場合は最後の報告でその旨を伝える。

### 3. メッセージを読む

各チャンネルを `slack_read_channel`（`oldest` / `latest` 指定）で読む。

**まず `response_format: "concise"` で読むこと。** このワークスペースには
仕様書や議事録を丸ごと1メッセージに貼る習慣があり、`detailed` で読むと
1件で数万字返ってきてコンテキストを食い潰す（実際に起きた）。
concise で見出しを掴んでから、案件に関係しそうなメッセージだけ
`slack_read_thread` や `detailed` で深掘りする方が速いし確実。

`thread_info` が付いているメッセージのスレッドは読む価値が高い。
**商談の結論はスレッドの中にあることが多い**ので、ここを飛ばすと表が
「〜について相談中」だらけになって使い物にならない。
ただし全スレッドを開くのではなく、金額・期日・合意が出てきそうなものを選ぶ。

以下は案件ではないので落とす：`◯◯さんがチャンネルに参加しました` 等の
システムメッセージ、本文が空でファイルだけの投稿（ただしファイル名が
`見積書_◯◯.pdf` のように案件情報を含む場合は動きとして拾う）。

### 4. 案件に組み立てる

**顧客ごとに名寄せする。** 同じ顧客の話が複数チャンネルに散っていても1行にまとめる。
1顧客で明らかに別案件が並走している場合だけ、案件名で行を分ける。

フェーズは次の語彙に寄せる（現場の言い回しからの対応の目安）：

| フェーズ | Slackでの現れ方 |
| --- | --- |
| リード | 問い合わせがあった、紹介をもらった |
| 初回接触 | アポ取得、初回訪問、ヒアリング |
| 提案 | 提案書送付、デモ実施、企画持ち込み |
| 見積 | 見積提出、金額提示、条件すり合わせ |
| 交渉 | 稟議中、値引き調整、契約書レビュー |
| 受注 | 発注、契約締結、受注確定 |
| 失注 | 見送り、他社決定、予算取れず |
| 保留 | 先方都合で止まっている、時期未定 |

**金額** は円の整数にする（`300万` → `3000000`、`¥50,000` → `50000`）。
月額と一括が混ざる場合は年額換算せず、書かれた金額をそのまま入れ、
「今週の動き」に `月額` と明記する。

**受注確度** は Slackに `確度70%` のような明記があればそれを使う。
明記がなければフェーズからの目安（リード10／初回接触20／提案40／見積60／交渉80／受注100／失注0／保留は空欄）を入れ、
**推定値であることが分かるよう「リスク・滞り」欄に `確度はフェーズからの推定` と書く**。

**ここが一番大事**：Slackに書かれていないことは埋めない。
金額も期日も担当も、分からなければ `null`（空欄）にする。
この表は会議で「じゃあこの金額で」と使われるので、それらしい数字を作ると
実害が出る。空欄は「Slackに書いてない＝誰かが確認する必要がある」という情報として役に立つ。

**出典** は必ず入れる。`#チャンネル名 2026-09-08 18:27` の形式。
permalinkは `https://ragnize.slack.com/archives/<チャンネルID>/p<tsからドットを除いた値>` で組み立てられる
（例: ts `1787882420.865549` → `p1787882420865549`）。分かる場合はURLも併記する。
読む人が「本当にそう書いてあるのか」を数秒で確かめられるかどうかで、この表の信用が決まる。

### 5. 案件JSONを書く

作業ファイルはスクラッチパッドに置く（リポジトリを汚さない）。

```json
{
  "period": {"start": "2026-09-04 15:00", "end": "2026-09-11 15:00"},
  "generated_at": "2026-09-11 15:02",
  "deals": [
    {
      "customer": "株式会社マックス",
      "deal": "AI研修パッケージ導入",
      "phase": "見積",
      "amount_yen": 3000000,
      "probability": 60,
      "this_week": "9/8に見積書を送付。先方の情シスからセキュリティ要件の追加質問あり。",
      "next_action": "セキュリティチェックシートを返送",
      "due": "2026-09-18",
      "owner": "須川翔太",
      "risk": "情シス確認が長引くと今期中の受注が厳しい",
      "source": "#株式会社マックス 2026-09-08 18:27"
    }
  ]
}
```

| キー | 内容 | 未記載のとき |
| --- | --- | --- |
| `customer` | 顧客名 | （必須） |
| `deal` | 案件名 | 顧客名＋商材で補う |
| `phase` | 上表のフェーズ | `保留` |
| `amount_yen` | 金額（円・整数） | `null` |
| `probability` | 受注確度（0-100の整数） | `null` |
| `this_week` | 期間内に起きたこと。日付入りで具体的に | `null` |
| `next_action` | 次に誰が何をするか | `null` |
| `due` | 期日 `YYYY-MM-DD` | `null` |
| `owner` | 担当者名 | `null` |
| `risk` | 滞り・懸念・推定の注記 | `null` |
| `source` | 出典 | （必須） |

### 6. Excelを作る

```bash
python3 .claude/skills/sales-weekly-report/scripts/build_xlsx.py <deals.json> <出力先.xlsx>
```

`openpyxl` が無ければ `pip3 install openpyxl`。
スクリプトが並び順（フェーズ順→加重金額順）、書式、色分け、サマリ集計を担当する：
期日超過と失注は赤、期日3日以内は黄、受注は緑。**この部分を自分で書き直さないこと** —
毎週同じ見た目で出てくることが、この表が読み慣れられる理由になっている。

### 7. Slackに投稿する

投稿先は `#営業進捗管理`。ユーザーは**この週次サマリをこのチャンネルに投稿することを事前に承認済み**なので、
毎週金曜の定期実行では確認を取らずに `slack_send_message` してよい。

一方で次の場合は**投稿前に必ずユーザーの確認を取る**。Slackへの投稿は取り消せず
チーム全員が読むので、もらった承認の範囲を勝手に広げないことが大事：

- `#営業進捗管理` 以外のチャンネルに投稿するとき
- 失注の原因や特定個人の動きなど、当人が読んで角が立つ書き方になっているとき
- ユーザーが対話の中で頼んだ単発の実行（定期実行ではないとき）

**このSlack連携ではファイルをアップロードできない。** 送れるのはテキストだけで、
添付の手段が無い。だから**xlsxをSlackに上げようとしないこと**（できずに時間を溶かす）。
運用はユーザーと合意済みで、**Slackにはテキストのサマリだけを投稿し、
Excelはユーザーが手元にダウンロードして必要なら自分でSlackに上げる**。
そのため投稿の締めは「詳細は添付のExcel」ではなく、**Excelは別途共有される旨**を書く。

文面の型：

```
📊 営業進捗サマリ（9/4〜9/11）

案件 12件 ／ 金額合計 2,840万円 ／ 加重 1,510万円

🔥 動いた案件
・株式会社マックス（見積・300万）… 見積送付済、セキュリティ要件の確認待ち
・◯◯市（交渉・180万）… 稟議中、9/19に結果

⚠️ 止まっている・要対応
・株式会社△△（提案）… 2週間返信なし、再アプローチが必要
・□□商事（見積）… 期日9/9を超過

案件一覧・リード一覧のExcelは別途共有します。
```

長くなりすぎないように、動いた案件と要対応を **各3〜5件** に絞る。
全件はExcelにあるので、投稿では「今週これを見てほしい」を選ぶ方が役に立つ。

## リード管理（Gmail）

振り分けの基準・対象外の見分け方・返信文面の型は
`references/lead-routing.md` に置いてある。**リードを触る前に必ず読むこと。**
ここ（SKILL.md）には手順だけを書く。

### 8. リードを集める

受け口は2つある。

- **`contact@ragnize.com`** … HPの問い合わせ窓口。`to:contact@ragnize.com` で検索。
  ただし届くものの大半は**他社からRAGNIZEへの営業**なので、そのまま一覧に入れない。
- **`label:RAGNIZE`**（m.natsume@ragnize.com 宛）… 進行中の商談メールが流れている。
  ニュースレター・銀行通知・名刺アプリ通知・Slack通知と混在しているので、
  人が書いた・相手が返事を待っている本文だけを拾う。

```
query="to:contact@ragnize.com newer_than:30d"
query="label:RAGNIZE newer_than:14d"
```

ラベル検索は**表示名で指定する**（`label:RAGNIZE`）。
ラベルIDで書くと0件が返ってくる。実際にこれで空振りした。

**検索結果のプレビューは古い方から5件しか返らない。**
新しいメッセージがあっても省略されるうえ、省略の印も出ない。
「返信したか／相手が待っているか」はこれでは絶対に判断できないので、
**候補に残したスレッドは必ず `get_thread` で開く**（`messageFormat: "METADATA_ONLY"` なら安い）。
実際にこれを飛ばしかけて、3日後に迫った打合せの出欠依頼を見落とすところだった。

### 9. 振り分ける

`references/lead-routing.md` の表に沿って、リードごとに決める。

- **製品** … QRPhone／FDE／Workforce／マドモアゼルai／その他
- **ステージ** … 未対応／返信済／商談化／クローズ／対象外
- **要返信（`awaiting_reply`）** … スレッドの最新メッセージが先方からで、こちらが返していないなら true

**すでに `リード/…` ラベルが付いているスレッドは、そのラベルが正。**
人が手で動かした結果を機械が巻き戻すと、この仕組み自体が使われなくなる。
ステージを変えるのは、メールの内容が明確に次へ進んだことを示しているときだけ。

判定したらGmailにラベルを付ける（`label_thread`）。ステージのラベルと製品のラベルを1つずつ。
1つのリードが複数スレッドにまたがっている場合（日程調整と資料送付が別スレッドなど）は、
**関係するスレッド全部に同じラベルを付ける**。後からGmailで検索したときに揃っている方が役に立つ。

### 10. 返信の下書きを作る

`awaiting_reply` が true のリードについて、`create_draft` で下書きを作る。
**送信は絶対にしない。** 判断を含む文面を機械が送るのは範囲外で、
人が読んで一手直しする前提で置いておくのが正しい姿。

- `replyToMessageId` に**先方の最新メッセージのID**を渡す（スレッドにぶら下がる）
- CCは受信メールに付いていた宛先をそのまま引き継ぐ。商談メールでCCを落とすのは事故になる
- 文面の型と、冒頭に必ず置く**確認ブロック**は `references/lead-routing.md` を参照

Excelの「返信下書き」欄には `作成済` / `不要` / `未作成` のいずれかを入れる。

### 11. リード一覧をExcelに載せる

案件JSONに `leads` 配列を足すだけでよい。スクリプトが「リード一覧」シートを作る。

```json
{
  "received": "2026-09-11",
  "company": "NTT西日本 中国支店",
  "person": "大庭 俊久",
  "email": "toshihisa.ooba.zv@west.ntt.co.jp",
  "product": "QRPhone",
  "stage": "商談化",
  "awaiting_reply": true,
  "summary": "はつかいちDMO様との打合せが9/14(月)13:30-15:00に決定。冒頭30分をAIボイスボットの枠にしたいとのこと。出欠の回答が必要。",
  "next_action": "9/14打合せの出欠を回答",
  "due": "2026-09-14",
  "owner": "須川翔太",
  "reply_draft": "作成済",
  "source": "Gmail「RE: はつかいちDMO向け提案について」2026-09-11 12:10"
}
```

一覧に載せる範囲は、**オープンなリード全部**（未対応・返信済・商談化）＋
その週にクローズ／対象外になったもの。オープンなリードは先週分も翌週分も載り続ける。
そうでないと「進捗を追う」にならない。

`awaiting_reply` の行は色でも並び順でも最優先で上に来る。
これがこの表の主役で、**今週誰を待たせているかが一目で分かること**が目的。

### メールは金額の出どころでもある

Slackには金額がほとんど書かれないが、メールには見積のプランや単価が出てくる。
リードを読んでいる途中で金額・プラン・期日が分かったら、**案件表の方も更新する**。
別々の作業にせず、読んだものを両方に反映するのが早い。
ただし見積がPDF添付で本文に金額が無い場合は、**推測せず空欄のまま**にして
「金額はPDF添付のため本文に記載なし」とリスク欄に書く。

## 12. ファイルを渡す（最後に一度）

`SendUserFile` があれば xlsx を送る。無ければ保存先の絶対パスを伝える。
**このコンテナは一定時間で破棄されるので、「手元にダウンロードしてください」と必ず添える。**
Slackに上げたい場合はユーザーが自分で上げる運用になっている（手順7を参照）。

最後に次を一言添える：

- 見たチャンネル数・メール件数（絞り込んだ場合はその旨も）
- 金額や期日が未記載で空欄になった件数
- 作った返信下書きの件数と、どのリード宛か
- 付けたGmailラベルの件数

**空欄が多いこと自体が「情報がSlackにもメールにも落ちていない」というレポート**なので、隠さず伝える。
それが分かれば、商談で金額を出したときにSlackに一行書く、といった運用の改善につながる。

## 定期実行（毎週金曜15:00 JST）

`create_trigger` で登録する。cronはUTC評価なので **金曜15:00 JST = `0 6 * * 5`**。
定期実行のプロンプトには、このスキルを使うこと・期間・投稿先チャンネルを明記しておく
（新しいセッションは文脈を持たずに始まるため）。
