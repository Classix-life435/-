# 営業週次レポート（Slack → Excel）

Slackに流れている商談の断片を、**そのまま読める一枚の案件表**にする。
使う人は営業会議の直前にこれを開くので、大事なのは網羅性よりも
「どの案件が今どうなっていて、次に誰が何をするのか」が一目で分かること。

## 出力するもの

1. **Excel**（`営業進捗_YYYYMMDD.xlsx`）— サマリシート＋案件一覧シート
2. **Slackサマリ投稿** — `#営業進捗管理` にテキストで要点を投稿（投稿前に必ずユーザーの確認を取る）
3. 生成したxlsxをユーザーに渡す（`SendUserFile` があればそれで、なければ保存先パスを伝える）

## 進め方

### 1. 集計期間を決める

既定は **直近1週間**：前週の金曜15:00（JST）〜 実行時点。
ユーザーが期間を指定したらそちらを優先する。

Slackの `oldest` / `latest` はUnix秒なので変換しておく：

```bash
python3 -c "
from datetime import datetime, timedelta, timezone
jst = timezone(timedelta(hours=9))
end = datetime.now(jst)
start = end - timedelta(days=7)
print('oldest', int(start.timestamp()))
print('latest', int(end.timestamp()))
print(start.strftime('%Y-%m-%d %H:%M'), '->', end.strftime('%Y-%m-%d %H:%M'))
"
```

### 2. 対象チャンネルを毎回探す

チャンネルは固定しない。営業の話は専用チャンネルだけでなく顧客名チャンネル
（`#株式会社◯◯`、`#◯◯市` など）でも進むので、取りこぼさないよう2方向から探す：

- `slack_search_public_and_private` で **メッセージ本文** を期間内検索する。
  **キーワードは1語ずつ、別々に検索する。** Slack検索はスペース区切りがANDなので、
  `商談 見積 提案 受注` のようにまとめて投げると全部を含むメッセージだけが対象になり、
  ほぼ確実に0件になる。実際にこの失敗をした。

  ```
  query="案件 after:2026-09-04"    sort="timestamp"
  query="見積 after:2026-09-04"    sort="timestamp"
  query="商談 after:2026-09-04"    sort="timestamp"
  ```

  回す語：`案件` `商談` `見積` `提案` `受注` `失注` `契約` `発注` `稟議` `デモ` `アポ` `訪問` `導入` `御中` `様`
  → ヒットしたメッセージが載っているチャンネルが、その週の実際の営業現場。
- `slack_search_channels`（`channel_types: public_channel,private_channel`）で
  `営業` `案件` `株式会社` などの**チャンネル名**も拾う。
  ただしチャンネル名検索は取りこぼしがある（`#営業案件` が `営業` で出てこないことがあった）ので、
  **メッセージ本文検索の方を主、チャンネル名検索を従として扱う。**

このワークスペース（ragnize）で実際に営業の話が進んでいたチャンネルの例：
`#営業案件` `#営業進捗管理` `#営業kpi` `#fde案件` `#nttプロジェクト` `#ロードカー営業`
`#契約書法務` `#qr-phone` `#ジャパックス` および顧客名チャンネル。
これは**当たりをつけるためのヒントであって固定リストではない**。毎回の検索結果を優先する。

両者のチャンネルIDを重複排除する。多すぎる場合は
「営業系チャンネル」＋「期間内に営業キーワードのヒットがあったチャンネル」を優先し、
**最大15チャンネル程度**に絞る。絞った場合は最後の報告でその旨を伝える。

### 3. メッセージを読む

各チャンネルを `slack_read_channel`（`oldest` / `latest` 指定）で読む。
`thread_info` が付いているメッセージは `slack_read_thread` も読む。
**商談の結論はスレッドの中にあることが多い**ので、ここを飛ばすと表が
「〜について相談中」だらけになって使い物にならない。

以下は案件ではないので落とす：`◯◯さんがチャンネルに参加しました` 等の
システムメッセージ、本文が空でファイルだけの投稿（ただしファイル名が
`見積書_◯◯.pdf` のように案件情報を含む場合は動きとして拾う）。

### 4. 案件に組み立てる

**顧客ごとに名寄せする。** 同じ顧客の話が複数チャンネルに散っていても1行にまとめる。
1顧客で明らかに別案件が並走している場合だけ、案件名で行を分ける。

フェーズは次の語彙に寄せる（現場の言い回しからの対応の目安）：

| フェーズ | Slackでの現れ方 |
| --- | --- |
| リード | 問い合わせがあった、紹介をもらった |
| 初回接触 | アポ取得、初回訪問、ヒアリング |
| 提案 | 提案書送付、デモ実施、企画持ち込み |
| 見積 | 見積提出、金額提示、条件すり合わせ |
| 交渉 | 稟議中、値引き調整、契約書レビュー |
| 受注 | 発注、契約締結、受注確定 |
| 失注 | 見送り、他社決定、予算取れず |
| 保留 | 先方都合で止まっている、時期未定 |

**金額** は円の整数にする（`300万` → `3000000`、`¥50,000` → `50000`）。
月額と一括が混ざる場合は年額換算せず、書かれた金額をそのまま入れ、
「今週の動き」に `月額` と明記する。

**受注確度** は Slackに `確度70%` のような明記があればそれを使う。
明記がなければフェーズからの目安（リード10／初回接触20／提案40／見積60／交渉80／受注100／失注0／保留は空欄）を入れ、
**推定値であることが分かるよう「リスク・滞り」欄に `確度はフェーズからの推定` と書く**。

**ここが一番大事**：Slackに書かれていないことは埋めない。
金額も期日も担当も、分からなければ `null`（空欄）にする。
この表は会議で「じゃあこの金額で」と使われるので、それらしい数字を作ると
実害が出る。空欄は「Slackに書いてない＝誰かが確認する必要がある」という情報として役に立つ。

**出典** は必ず入れる。`#チャンネル名 2026-09-08 18:27` の形式。
permalinkは `https://ragnize.slack.com/archives/<チャンネルID>/p<tsからドットを除いた値>` で組み立てられる
（例: ts `1787882420.865549` → `p1787882420865549`）。分かる場合はURLも併記する。
読む人が「本当にそう書いてあるのか」を数秒で確かめられるかどうかで、この表の信用が決まる。

### 5. 案件JSONを書く

作業ファイルはスクラッチパッドに置く（リポジトリを汚さない）。

```json
{
  "period": {"start": "2026-09-04 15:00", "end": "2026-09-11 15:00"},
  "generated_at": "2026-09-11 15:02",
  "deals": [
    {
      "customer": "株式会社マックス",
      "deal": "AI研修パッケージ導入",
      "phase": "見積",
      "amount_yen": 3000000,
      "probability": 60,
      "this_week": "9/8に見積書を送付。先方の情シスからセキュリティ要件の追加質問あり。",
      "next_action": "セキュリティチェックシートを返送",
      "due": "2026-09-18",
      "owner": "須川翔太",
      "risk": "情シス確認が長引くと今期中の受注が厳しい",
      "source": "#株式会社マックス 2026-09-08 18:27"
    }
  ]
}
```

| キー | 内容 | 未記載のとき |
| --- | --- | --- |
| `customer` | 顧客名 | （必須） |
| `deal` | 案件名 | 顧客名＋商材で補う |
| `phase` | 上表のフェーズ | `保留` |
| `amount_yen` | 金額（円・整数） | `null` |
| `probability` | 受注確度（0-100の整数） | `null` |
| `this_week` | 期間内に起きたこと。日付入りで具体的に | `null` |
| `next_action` | 次に誰が何をするか | `null` |
| `due` | 期日 `YYYY-MM-DD` | `null` |
| `owner` | 担当者名 | `null` |
| `risk` | 滞り・懸念・推定の注記 | `null` |
| `source` | 出典 | （必須） |

### 6. Excelを作る

```bash
python3 .claude/skills/sales-weekly-report/scripts/build_xlsx.py <deals.json> <出力先.xlsx>
```

`openpyxl` が無ければ `pip3 install openpyxl`。
スクリプトが並び順（フェーズ順→加重金額順）、書式、色分け、サマリ集計を担当する：
期日超過と失注は赤、期日3日以内は黄、受注は緑。**この部分を自分で書き直さないこと** —
毎週同じ見た目で出てくることが、この表が読み慣れられる理由になっている。

### 7. Slackに投稿する（確認してから）

`#営業進捗管理` 宛てのサマリ文面を作り、**ユーザーに見せて承認を取ってから** `slack_send_message` する。
自動実行のときも同じで、承認が取れない場面では投稿せずファイルだけ渡し、
その旨を報告する（勝手に全社が見るチャンネルに投稿しない）。

文面の型：

```
📊 営業進捗サマリ（9/4〜9/11）

案件 12件 ／ 金額合計 2,840万円 ／ 加重 1,510万円

🔥 動いた案件
・株式会社マックス（見積・300万）… 見積送付済、セキュリティ要件の確認待ち
・◯◯市（交渉・180万）… 稟議中、9/19に結果

⚠️ 止まっている・要対応
・株式会社△△（提案）… 2週間返信なし、再アプローチが必要
・□□商事（見積）… 期日9/9を超過

詳細は添付のExcelをご確認ください。
```

長くなりすぎないように、動いた案件と要対応を **各3〜5件** に絞る。
全件はExcelにあるので、投稿では「今週これを見てほしい」を選ぶ方が役に立つ。

### 8. ファイルを渡す

`SendUserFile` があれば xlsx を送る。無ければ保存先の絶対パスを伝える。
最後に、絞り込んだチャンネル数・拾えなかった情報（金額未記載が何件あるか等）を
一言添える。**空欄が多いこと自体が「Slackに情報が落ちていない」というレポート**なので、隠さず伝える。

## 定期実行（毎週金曜15:00 JST）

`create_trigger` で登録する。cronはUTC評価なので **金曜15:00 JST = `0 6 * * 5`**。
定期実行のプロンプトには、このスキルを使うこと・期間・投稿先チャンネルを明記しておく
（新しいセッションは文脈を持たずに始まるため）。
